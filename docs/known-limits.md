# Known limits

This file lists five weaknesses in this demo that are known and not fixed, with what can go wrong, when, and what a real deployment would need.

- **Gateway login:** The demo gateway runs with authentication off, bound to loopback, which means reachable only from the same machine. `config/permissions.json` maps the client name `gateway-client` to the person Marcus, so any process on that machine can connect under that name and act as him. A real deployment needs gateway authentication and an identity taken from the login, not from a name the client sends.
- **Bulk update is not all-or-nothing:** The Salesforce mock applies a bulk update one account at a time. If one account id is unknown, the accounts before it stay changed and the call reports an error. A real integration should check every id first or roll the whole batch back.
- **Memory lock:** A lock is a marker file that keeps two writers from changing one user's notes at once. A writer that pauses for longer than 30 seconds can lose its lock to another writer, then finish and overwrite the newer notes. It needs an exact interleave of the two writers and was never observed. A real deployment would need a lock that proves who owns it before it writes or releases.
- **PartnerStack defaults to the mock:** With `backend` left out, the plugin uses the in-memory mock, which is a stand-in kept in memory. A write looks successful and nothing reaches PartnerStack, while the approval prompt still says real money moves. A real deployment must set `backend: "http"` on purpose and should refuse to start without it.
- **A repeated payment by a different person:** The idempotency key, which is the key that stops a repeated request from paying twice, includes the person who asked. If a payment goes through but its answer is lost, a second person retrying the same payment gets a new key and can pay it again. A real deployment should build that key from the payment itself and keep the person only as a record of who asked.
